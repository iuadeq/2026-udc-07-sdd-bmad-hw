# A/B: зі специфікацією проти ad-hoc (Task D)

**Фіча:** знижки з `materials/feature-request.md`
**Хост / модель:** Claude Code / Claude Opus 4.6

## Прогін A — зі специфікацією

Агенту дано `docs/spec/pricing-discounts.md` і сказано реалізувати за нею.

- **Що вийшло:** `app/src/discounts.ts` — один модуль з `priceOrder()` і
  `PriceBreakdown` інтерфейсом. Чіткий data flow: tier → validate coupons →
  scope-winner selection → floor → total.
- **Рішення щодо неоднозначностей:** повністю збіглись зі спекою — кожне
  рішення D-1…D-12 реалізоване буквально, бо код писався за специфікацією.
- **Тести:** 12 тестів, названі за AC-1…AC-12 з конкретними числами.
  Покриті всі граничні випадки: порожнє замовлення, від'ємний підсумок,
  пів копійки, дублікати.

## Прогін B — ad-hoc

**Новий** чат. Агенту (Claude Opus 4.6) дано **лише** `materials/feature-request.md`
і вихідний код (`types.ts`, `pricing.ts`) — без спеки.

- **Що вийшло:** `/tmp/adhoc-discounts.ts` — простіший модуль без
  `appliedCoupons`/`skippedCoupons` (просто `discountKopecks`). Без
  `now` параметра (тестування expiration нестабільне).
- **Які розвилки він вирішив мовчки:**
  - D-1: **адитивне** складання (обидва від subtotal) — мовчки
  - D-3: **всі купони застосовуються**, без ліміту на scope — мовчки
  - D-4: `Math.floor` замість `Math.round` — мовчки
  - D-6: minSubtotal перевіряється **після** tier discount — мовчки
  - D-11: **без дедуплікації** — один код працює двічі — мовчки
  - D-12: фіксований купон **не обрізається** до бази — мовчки
- **Тести:** оцінка агента — 5–6 тестів. Без граничних випадків (порожнє
  замовлення, пів копійки, дублікати, coupon > base не тестувались).

## Висновок

Агент без специфікації мовчки вирішив інакше **6 з 12** розвилок, причому
щонайменше 4 з цих рішень є об'єктивними багами (D-3: подвійне купонування
на ту саму категорію, D-6: minSubtotal перевіряється після знижки — клієнт
може втратити купон через tier, D-11: дублікат коду дає подвійну знижку,
D-12: фіксований купон знижує більше, ніж вартість товарів).

Чи помітив би я це на code review без специфікації? D-11 і D-12 — можливо.
D-3 і D-6 — навряд чи: вони виглядають «робочими», поки не подумаєш про
конкретні сценарії.

**Ціна vs користь:** специфікація коштувала ~30 хв додаткового часу. На цій
задачі вона окупилась: 4 латентні баги × потенційні фінансові втрати на
production (дублювання знижок, подвійне купонування) значно дорожчі за
30 хвилин аналітичної роботи. Але для фічі без грошових наслідків (напр.
зміна порядку сортування) цей overhead був би надмірним. SDD окупається
насамперед на логіці з **комбінаторними edge cases** і **фінансовими
наслідками помилок**.
