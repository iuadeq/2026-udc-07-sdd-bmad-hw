# SDD-інструмент: OpenSpec (Task B)

**Інструмент:** [OpenSpec](https://github.com/Fission-AI/OpenSpec) v1.13.0
**Рантайм:** Node.js (глобальний npm-пакет `@fission-ai/openspec`)
**Встановлення:** `npm install -g @fission-ai/openspec@latest`, потім `openspec init --tools claude`

## Що він згенерував

OpenSpec створив структуру `openspec/` з конфігом і теку зміни
`openspec/changes/pricing-discounts/` із чотирма артефактами за схемою
`spec-driven`:

| Артефакт | Файл | Призначення |
|---|---|---|
| **proposal.md** | `openspec/changes/pricing-discounts/proposal.md` | Мотивація зміни: навіщо, що змінюється, які capabilities |
| **spec.md** | `openspec/changes/pricing-discounts/specs/pricing-discounts/spec.md` | Вимоги в структурованому форматі (REQ-*) + сценарії (SC-*) |
| **design.md** | `openspec/changes/pricing-discounts/design.md` | Архітектурні рішення: data flow, альтернативи |
| **tasks.md** | `openspec/changes/pricing-discounts/tasks.md` | Чек-ліст задач для реалізації, прив'язаний до REQ і AC |

Крім того, OpenSpec створив 6 Claude Code skills у `.claude/skills/` і 6
slash-команд у `.claude/commands/opsx/` для інтеграції з Claude Code CLI.

## Що він дав понад звичайну markdown-специфікацію

1. **Структурований workflow з залежностями.** OpenSpec не дає писати `tasks.md`
   поки немає `proposal` → `specs` → `design`. Це змушує думати в правильному
   порядку: мотивація → вимоги → архітектура → план. Мій markdown-документ
   (Task A) мав усе це в одному файлі, але без явного примусу до послідовності.

2. **Машинно-читабельний статус.** `openspec status --json` показує, які
   артефакти готові, які заблоковані, що треба створити далі. Для одного файлу
   це надлишково, але для проєкту з десятками specs це корисний інструмент
   відстеження.

3. **CLI-валідація.** `openspec validate` перевіряє, що зміна має capabilities,
   що всі залежності задоволені. Це не перевіряє зміст — але ловить структурні
   помилки (забули spec, забули tasks).

4. **Claude Code інтеграція.** Skills дозволяють запускати
   `/opsx:propose`, `/opsx:apply` прямо з Claude Code. Зручно для тих, хто
   працює в CLI, але не додає нічого для вмісту специфікації.

## Що довелося робити руками

- **Увесь зміст** — OpenSpec створює порожні шаблони, але не аналізує бізнес-тікет
  і не знаходить неоднозначності. Таблицю рішень (D-1…D-12), критерії приймання
  (AC-1…AC-12), контракт — усе це я написав сам у Task A. OpenSpec лише
  структурував цю роботу в 4 окремі файли замість одного.
- **Маппінг між форматами.** Моя специфікація (Task A) використовує формат AC-N,
  а OpenSpec хоче REQ-*/SC-*. Довелося транслювати вручну.
- **Ініціалізація** вимагала явного прапорця `--tools claude` — без нього `init`
  відмовляється працювати.

## Висновок

Для задачі такого розміру (одна фіча, один модуль) OpenSpec додав **організаційну
структуру** (розділення concerns на 4 файли, залежності між ними, CLI-статус),
але **не додав жодної інтелектуальної роботи** — усі рішення щодо неоднозначностей
і критерії приймання залишились повністю на мені. Інструмент корисний як рамка
для більших проєктів із кількома паралельними changes, але для одного discount
engine звичайний markdown із чіткою структурою був би достатнім.
